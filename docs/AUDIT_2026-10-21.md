## Reproduced defects and fixes

1. **Offscreen joints produced plausible numeric values.** A wrist at normalized
   image X=1.2 with high model visibility still displayed a 0-degree elbow angle.
   Image X/Y now must be finite and within [0, 1]. The affected filtered landmark
   is invalidated immediately; its next valid observation starts fresh. Other
   reliable joints remain available. Offscreen torso anchors also invalidate the
   shoulder/hip body frame, with an explicit reason.
2. **Capture gaps retained old pose history.** A known 90-degree elbow after a
   0.5-second gap displayed 84.4497 degrees because smoothing bridged the unseen
   interval. Gaps over 0.25 seconds now reset filter history before the new pose;
   the deterministic recovery fixture returns 90 degrees.
3. **A stalled camera kept old values visible.** Previously the app waited up to
   three seconds for its terminal stall error. When the loop can poll again, a
   0.25-second gap now clears the feed and values to `Camera frame stale`. A single
   status redraw is issued per stall, without inference, callback samples or FPS
   inflation. Fresh input restores normal processing.
4. **Slow inference could publish expired numbers.** A simulated 300 ms model
   call returned twelve numeric values. Frame age is now checked before rendering;
   expired values and overlays are withheld, and reference collection receives
   unavailable metrics. The model call is still timed and the processed frame
   still contributes to actual throughput statistics.

The 0.25-second threshold is an explicit freshness heuristic, not a clinical
accuracy threshold or a substitute for the 30 FPS requirement. The polling interval
is 50 ms; a blocking native model/display call cannot be preempted. Projection
angles remain geometric proxies: simultaneous multi-plane shoulder motion is not
a clinically calibrated joint-coordinate decomposition, and a torso frame is not
a calibrated scapular/pelvic frame. These limits are retained in the README.

## Software follow-up — physical verification deferred

Reviewed baseline `2d4b1bdbdc4373cefc14538e3c3efb005753d531` after the user asked
to defer actual webcam/assessor verification and fix remaining software issues.
The following failures were reproduced with deterministic fixtures before repair:

1. **Camera metadata could be wrong or non-serializable.** Drivers returning zero,
   negative, NaN or infinite properties could report a false resolution or make
   strict JSON export fail. Reported/requested 1280×720 also hid actual 640×480
   input. Resolution now comes from received image dimensions. Until a first
   frame arrives it is unknown; unsupported nominal FPS is `None`/JSON `null`.
   Restart clears previous metadata. This nominal FPS is separate from measured
   end-to-end throughput. Tests cover real asynchronous capture and the shared
   benchmark/export path, not only a sanitization helper.
2. **Slow rendering or native event pumping could publish expired numbers.**
   The earlier freshness gate only ran before rendering. Simulated 300 ms delays
   exposed numeric frames/callbacks beyond the 0.25-second freshness policy.
   Rendering now has a second gate before display submission. A slow display
   call invalidates callback values and clears the screen once it returns, unless
   the user has quit/closed it. Status output starts with a blank image so an old
   translucent numeric HUD cannot remain underneath. These refreshes do not add
   inference calls, processed frames, FPS samples or hold observations. Their
   cleanup time is included in the corresponding frame's pipeline latency.
   Native calls still cannot be interrupted while blocked; this is not a hard
   real-time display guarantee.
3. **Cancelling before the first frame could crash validation collection.**
   Unknown resolution exposed an `int(None)` conversion while creating an empty
   hold. Collection now returns code 2 with an explicit no-frames message and
   leaves the CSV unchanged when no frame was processed.
